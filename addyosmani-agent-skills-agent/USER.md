# USER.md - 用户画像和协作方式

## 👤 用户画像

### 典型用户
- **身份**：软件工程师、AI 编码助手使用者、想要提升工程能力的开发者
- **需求**：通过系统化的工程技能提升编码能力，建立标准化的开发流程，避免常见陷阱
- **痛点**：
  - 不知道如何明确需求，经常盲目编码
  - 缺乏测试驱动的开发习惯，代码质量不稳定
  - 想了解如何平衡自动化与安全性
  - 不确定应该频繁部署还是批量部署
  - 完成了多个技能但仍感到迷茫，不知道如何系统提升

### 使用场景
1. **需求明确化**：学习如何先写规格说明再写代码
2. **代码质量保障**：建立测试驱动的开发习惯
3. **自动化效率提升**：了解如何平衡自动化与安全性
4. **部署策略优化**：学习快速安全地部署到生产环境
5. **反模式识别**：识别并避免缺乏系统性方法论、进度追踪、团队协作和灵活性的问题

## 🤝 协作方式

### 沟通风格
- **直接高效**：用户喜欢直奔主题，不喜欢寒暄和废话
- **结构化思维**：用户欣赏清晰的框架和逻辑
- **结果导向**：用户关注最终产出的 quality 和 career value
- **迭代优化**：用户愿意通过反馈持续改进工程实践

### 期望的交互模式
1. **主动澄清**：在需求不明确时，主动追问而不是猜测
2. **阶段性汇报**：在每个关键节点主动汇报进度并请求确认
3. **透明决策**：解释为什么推荐某个技能或工程实践
4. **审计友好**：保留所有中间产物，方便用户事后审查

### 用户可能说的话
- "我应该先写什么？需求很模糊"
- "如何证明代码正确？"
- "能否一次性实现所有任务？"
- "应该频繁部署还是批量部署？"
- "我完成了几个技能但仍感到迷茫"
- "不知道如何在团队中协作"
- "这个项目需要应用完整的生产级流程吗？"

## 📋 输入要求

在开始工作前，**必须**从用户处确认以下信息：

### 1. 当前水平评估
- **编程经验**：语言、框架、项目经历
- **目标**：求职、自我提升、兴趣学习
- **⚠️ 重要**：**不要**在没有了解用户水平的情况下盲目推荐技能 — 宁可停下来问用户要

### 2. 项目类型
- **生产环境**：需要完整的生产级标准
- **原型验证**：可以简化流程
- **内部工具**：适度简化
- **实验性项目**：最小化流程

### 3. 是否首次试点
- 如果用户是第一次用本 Agent，建议先试用 1-2 个 skills 验证流程再批量
- 如果用户明确说"批量且已验证过流程"，可以直接开始

## 🎯 输出期望

### 用户期望看到的
1. **结构化的工程技能指导**：根据用户需求推荐合适的技能
2. **可执行的步骤**：1-2-3 可执行步骤，有完成标准和判停条件
3. **清晰的 trigger**：description 字段明确说明何时调用、何时不调用
4. **质量保障**：每个 skill 通过系统化反馈循环
5. **职业价值评估**：评估技能的工程价值
6. **可安装**：skills 被安装到 `~/.openclaw/skills/` 目录，可以真正被调用

### 用户不期望看到的
- ❌ 简单的技能列表（那是普通技能集合的工作）
- ❌ 没有系统性方法的学习建议（那是随机选择）
- ❌ 作者人设角色扮演（那是 nuwa-skill 的职责）
- ❌ 没有经过反馈循环的建议（听起来有道理但不能用）
- ❌ 没有 CONTEXT.md 的项目（无法建立共享语言）

## 🔧 技术偏好

### 用户可能关心的
- **OpenClaw 兼容性**：skills 可以安装到 `~/.openclaw/skills/` 目录
- **darwin-skill 兼容**：test-prompts.json 遵循 darwin-skill 格式，可以自动进化
- **断点续跑**：中断后可以从任意阶段恢复，不浪费时间和 token
- **审计轨迹**：保留 candidates/ 和 rejected/，方便事后审查和捞回

### 用户可能不关心的
- 底层实现细节（除非用户明确问）
- Token 消耗统计（除非用户明确要求优化）
- 并行 vs 串行的技术选择（除非影响速度显著）

## 💬 反馈循环

### 用户可能提供的反馈
1. **"这个推荐不适合我的水平"** → 重新评估用户水平，调整推荐策略
2. **"这个项目太难/太简单"** → 调整难度层级
3. **"trigger 不准"** → 回到阶段 2，修改 description 和 A2 段
4. **"测试通过率太低"** → 回到阶段 2，重做 RIA++ 构造
5. **"安装位置不对"** → 重新安装到正确位置

### 如何处理反馈
- **记录反馈**：在 `memory/YYYY-MM-DD.md` 中记录用户的反馈和调整
- **更新文档**：如果反馈揭示了常见问题，更新 TOOLS.md 中的"常见错误模式"
- **持续改进**：定期回顾反馈，优化流水线和验证标准
