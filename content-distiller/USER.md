# USER.md - 用户画像和协作方式

## 👤 用户画像

### 典型用户
- **身份**：知识工作者、终身学习者、内容创作者、Agent 开发者
- **需求**：把高价值内容（书籍、长视频、播客、课程）转化为可执行的 Agent Skills，让方法论真正用起来
- **痛点**：
  - 读了很多书，但记不住、用不上
  - 想要把书中的方法论固化成可复用的工具
  - 希望 agent 能在真实场景中自动调用这些方法论
  - 不想只是"读过"，而是想"用过"

### 使用场景
1. **个人学习**：把正在读的书蒸馏成 skills，建立个人知识库
2. **团队共享**：把团队必读的经典书籍蒸馏成 skills，统一方法论语言
3. **产品集成**：把行业最佳实践蒸馏成 skills，嵌入到产品中
4. **内容创作**：把长视频/播客蒸馏成 skills，二次创作结构化内容

---

## 🤝 协作方式

### 沟通风格
- **直接高效**：用户喜欢直奔主题，不喜欢寒暄和废话
- **结构化思维**：用户欣赏清晰的框架和逻辑
- **结果导向**：用户关注最终产出的 quality 和 usability
- **迭代优化**：用户愿意通过反馈持续改进 skill 质量

### 期望的交互模式
1. **主动澄清**：在需求不明确时（如缺少源文本），主动提问而不是猜测
2. **阶段性汇报**：在每个关键节点（阶段 0、1.5、5）主动汇报进度并请求确认
3. **透明决策**：解释为什么某个候选单元通过/不通过三重验证
4. **审计友好**：保留所有中间产物（candidates/、rejected/），方便用户事后审查

### 用户可能说的话
- "帮我拆《穷查理宝典》"
- "把毛选蒸馏成 skill"
- "把这个 B 站视频/播客/课程蒸馏成 skill"
- "distill this book into skills: <path>"
- "我想把这本书的方法论做成可用的 skill"
- "继续上次中断的《XXX》蒸馏"
- "把这 5 本书都蒸馏成 skills"
- "这个 skill 的 trigger 不准，经常误触发"

## 📋 输入要求

在开始蒸馏前，**必须**从用户处确认以下信息：

### 1. 内容文本来源
- **书籍**：PDF / EPUB / TXT 文件路径，或可访问的纯文本
- **视频/播客**：转写稿路径（建议先用 video-downloader 类工具拿到转写文本）
- **课程**：文字稿或字幕文件路径
- **⚠️ 重要**：**不要**在没有文本的情况下"凭记忆"蒸馏 — 宁可停下来问用户要

### 2. 内容元信息
- **书籍**：书名 + 作者 + 出版年
  - 例：《穷查理宝典》 / 查理·芒格 / 2005
- **视频/播客/课程**：标题 + 作者（UP 主/主播/讲者）+ 发布时间
  - 例："罗辑思维第 100 期" / 罗振宇 / 2015-03-15

### 3. 是否首次试点
- 如果用户是第一次用 content-distiller，建议先蒸馏 1 份内容验证流程再批量
- 如果用户明确说"批量且已验证过流程"，可以直接开始

### 4. 非书籍内容的字段映射
- `source_chapter` 等"章节"字段对视频填时间戳或分 P，对播客填集数，对课程填讲次 — 保证可追溯即可

## 🎯 输出期望

### 用户期望看到的
1. **结构化的 skills 目录**：每个 skill 有完整的 R/I/A1/A2/E/B 六段
2. **可执行的步骤**：E 段必须是 1-2-3 可执行步骤，有完成标准和判停条件
3. **清晰的 trigger**：description 字段明确说明何时调用、何时不调用
4. **质量保障**：每个 skill 通过三重验证和压力测试
5. **精华长文**：DIGEST.md 满足"不读全书、只看精华"的需求
6. **可安装**：skill 被安装到 `~/.openclaw/skills/` 目录，可以真正被调用

### 用户不期望看到的
- ❌ 简单的书摘或摘要（那是普通总结工具的工作）
- ❌ 读后感或情感共鸣分析（那是 nuwa-skill 的职责）
- ❌ 作者人设角色扮演（那是 nuwa-skill 的职责）
- ❌ 没有经过验证的方法论（听起来有道理但不能用）
- ❌ 没有 test-prompts.json 的 skill（无法进化）

## 🔧 技术偏好

### 用户可能关心的
- **OpenClaw 兼容性**：skills 可以安装到 `~/.openclaw/skills/` 目录
- **darwin-skill 兼容**：test-prompts.json 遵循 darwin-skill 格式，可以自动进化
- **断点续跑**：中断后可以从任意阶段恢复，不浪费时间和 token
- **审计轨迹**：保留 candidates/ 和 rejected/，方便事后审查和捞回

### 用户可能不关心的
- 底层实现细节（除非用户明确问）
- Token 消耗统计（除非用户明确要求优化）
- 并行 vs 串行的技术选择（除非影响速度显著）

## 💬 反馈循环

### 用户可能提供的反馈
1. **"骨架理解不对"** → 回到阶段 0，重新分析
2. **"这个候选应该通过/不通过"** → 调整三重验证标准，更新 verified.md
3. **"trigger 不准"** → 回到阶段 2，修改 description 和 A2 段
4. **"测试通过率太低"** → 回到阶段 2，重做 RIA++ 构造
5. **"安装位置不对"** → 重新安装到正确位置

### 如何处理反馈
- **记录反馈**：在 `memory/YYYY-MM-DD.md` 中记录用户的反馈和调整
- **更新文档**：如果反馈揭示了常见问题，更新 TOOLS.md 中的"常见错误模式"
- **持续改进**：定期回顾反馈，优化流水线和验证标准
