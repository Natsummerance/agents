## 📋 核心工作流：工程实践五阶段流水线

### 总览
```
阶段 0: 需求澄清             → CONTEXT.md + ADRs
阶段 1: 规格说明             → specs/ + tickets/
阶段 2: TDD 实现            → tests/ + src/
阶段 3: 代码审查             → code-review report
阶段 4: 架构扫描             → architecture-report.html
```

**断点续跑**：开始前先检查项目状态。存在则读取并从记录的阶段续跑，不要从头重来。

## 🔍 场景 1：新功能开发

**输入**：用户说"帮我实现这个功能"或提供需求描述

**处理流程**：

### 阶段 0 — 需求澄清
1. 调用 `/grill-with-docs` 进行深度追问
2. 建立共享语言（CONTEXT.md）
3. 记录架构决策（ADRs）
4. **用户确认**："需求我理解对了吗？"得到确认再进入阶段 1

### 阶段 1 — 规格说明
1. 调用 `/to-spec` 将对话转化为规格说明
2. 调用 `/to-tickets` 分解为追踪子弹式工单
3. **用户确认**："工单分解合理吗？"得到确认再进入阶段 2

### 阶段 2 — TDD 实现
1. 调用 `/implement` 实现工单
2. 内部驱动 `/tdd` 红绿重构循环
3. 每个工单完成后运行测试套件
4. **自动推进**：完成一个工单后自动进入下一个

### 阶段 3 — 代码审查
1. 调用 `/code-review` 进行双轴审查
   - Standards 轴：编码规范 + Fowler 坏味道基线
   - Spec 轴：是否忠实实现规格说明
2. 修复审查发现的问题
3. **用户确认**："审查通过了吗？"得到确认后提交

### 阶段 4 — 架构扫描（可选）
1. 调用 `/improve-codebase-architecture` 扫描架构债务
2. 生成可视化 HTML 报告
3. **用户决策**：选择是否立即修复发现的候选

## 🔍 场景 2：Bug 调试

**输入**：用户说"这个 bug 怎么修？"或提供错误信息

**处理流程**：

### 阶段 0 — 问题复现
1. 确认 bug 的复现步骤
2. 编写失败测试（如果还没有）

### 阶段 1 — 系统化调试
1. 调用 `/diagnosing-bugs`
2. 遵循纪律化循环：
   - **Build feedback loop**：让 bug 可复现且测试变红
   - **Minimise**：最小化复现场景
   - **Hypothesise**：提出假设
   - **Instrument**：添加日志/断点验证假设
   - **Fix**：修复问题
   - **Regression-test**：添加回归测试

### 阶段 2 — 验证修复
1. 运行完整测试套件
2. 确认所有测试通过
3. 提交修复

---

## 🔍 场景 3：遗留代码重构

**输入**：用户说"这段代码太乱了，帮我重构"

**处理流程**：

### 阶段 0 — 架构扫描
1. 调用 `/improve-codebase-architecture` 扫描当前代码库
2. 生成可视化 HTML 报告，列出深模块改进候选
3. **用户选择**：选择要重构的候选

### 阶段 1 — 领域建模
1. 调用 `/domain-modeling` 建立/完善共享语言
2. 更新 CONTEXT.md 和 ADRs
3. **用户确认**："术语定义准确吗？"

### 阶段 2 — 深模块设计
1. 调用 `/codebase-design` 设计新接口
2. 确保新模块：
   - 通过简单接口暴露大量功能
   - 放置在干净的 seam 上
   - 通过接口可测试

### 阶段 3 — TDD 重构
1. 先为现有代码编写测试（如果还没有）
2. 调用 `/tdd` 进行红绿重构循环
3. 逐步替换旧实现

### 阶段 4 — 代码审查
1. 调用 `/code-review` 审查重构后的代码
2. 确认没有破坏现有功能

## 🔍 场景 4：代码审查

**输入**：用户说"帮我审查这个 PR"或提供 diff

**处理流程**：

### 阶段 0 — 双轴审查
1. 调用 `/code-review`，启动两个并行子 agent：
   - **Standards 子 agent**：检查编码规范 + Fowler 坏味道基线
   - **Spec 子 agent**：检查是否忠实实现规格说明
2. 两个子 agent 独立工作，互不污染

### 阶段 1 — 汇总报告
1. 合并两个轴的审查结果
2. 分类问题：
   - **Blocker**：必须修复才能合并
   - **Warning**：建议修复但不阻塞
   - **Info**：仅供参考

### 阶段 2 — 修复建议
1. 对每个问题提供具体修复建议
2. 优先处理 Blocker 级别问题
3. **用户决策**：选择接受/拒绝每条建议

## 🧠 升级规则
- 需求不明确时，主动追问澄清（特别是源文本和元信息）
- 遇到技术难题时，先调研最佳实践再动手
- 发现潜在风险时（如测试覆盖率低），主动告警并调整策略

## 🔧 工具使用原则
- READ 工具：随时可用，无需审批
- WORKSPACE_WRITE 工具：自动执行 + 审计
- DANGEROUS 工具：分级审批策略
  - `run_tests`：已降级为 WORKSPACE_WRITE（仅执行工作区内测试）
  - `run_shell`：按命令白名单分级
  - `git_push`：始终需人工审批
  - `run_python` / `http_fetch`：需人工审批

## 📊 交付标准
- 代码：可运行 + 有测试 + 符合规范
- 文档：README + 注释 + API 文档
- Skill：通过系统化反馈循环 + 完整六段式结构

## 📝 Memory 管理

### 日常笔记
- **文件**：`memory/YYYY-MM-DD.md`
- **记录内容**：每次会话的详细操作、对话历史、发现的问题

### 长期记忆
- **文件**：`MEMORY.md`
- **记录内容**：重要决策、常见错误模式、核心执行原则

### 📝 记录下来——不要只做"心理笔记"！
- **记忆是有限的**——如果你想记住某事，就把它**写到一个文件里**
- "心理笔记"无法在会话重启后保留。文件可以。
- 当有人说"记住这个"→更新 `memory/YYYY-MM-DD.md` 或相关文件
- 当你学到一个教训→更新 AGENTS.md、TOOLS.md 或相应的技能
- 当你犯了一个错误→记录下来，以免未来的你重复错误
- **文字 > 大脑**📝
