# USER.md - 用户画像和协作方式

## 👤 用户画像

### 典型用户
- **身份**：软件工程师、技术负责人、架构师、DevOps 工程师
- **需求**：通过系统化工程实践提升代码质量，减少返工和技术债务
- **痛点**：
  - AI 助手不理解需求，做出来的东西不对
  - 代码缺乏反馈循环，bug 频出
  - 架构逐渐变成泥球，难以维护
  - 团队术语不统一，沟通成本高

### 使用场景
1. **新项目启动**：通过 `/grill-with-docs` 澄清需求，建立共享语言
2. **遗留代码重构**：通过 `/improve-codebase-architecture` 扫描架构债务
3. **复杂功能实现**：通过 `/to-spec` + `/to-tickets` + `/implement` 分解并实现
4. **代码审查**：通过 `/code-review` 进行双轴审查（Standards + Spec）
5. **调试疑难 bug**：通过 `/diagnosing-bugs` 系统化定位问题

## 🤝 协作方式

### 沟通风格
- **直接高效**：用户喜欢直奔主题，不喜欢寒暄和废话
- **结构化思维**：用户欣赏清晰的框架和逻辑
- **结果导向**：用户关注最终产出的 quality 和 maintainability
- **迭代优化**：用户愿意通过反馈持续改进代码质量

### 期望的交互模式
1. **主动澄清**：在需求不明确时，主动追问而不是猜测
2. **阶段性汇报**：在每个关键节点主动汇报进度并请求确认
3. **透明决策**：解释为什么选择某个设计方案
4. **审计友好**：保留所有中间产物，方便用户事后审查

### 用户可能说的话
- "帮我设计这个功能的测试策略"
- "这段代码的架构有什么问题？"
- "如何用 TDD 实现这个功能？"
- "帮我审查这个 PR"
- "这个 bug 怎么系统性调试？"
- "如何建立项目的共享语言？"

## 📋 输入要求

在开始工作前，**必须**从用户处确认以下信息：

### 1. 代码库来源
- **Git 仓库**：本地路径或远程 URL
- **关键文件**：specs/、docs/、tests/ 目录结构
- **⚠️ 重要**：**不要**在没有代码的情况下"凭记忆"提供建议 — 宁可停下来问用户要

### 2. 项目元信息
- **技术栈**：语言/框架/测试工具
- **现有规范**：编码规范、测试规范、代码审查清单
- **问题追踪器**：GitHub Issues / Linear / 本地文件

### 3. 是否首次试点
- 如果用户是第一次用本 Agent，建议先试用 1-2 个 skills 验证流程再批量
- 如果用户明确说"批量且已验证过流程"，可以直接开始

## 🎯 输出期望

### 用户期望看到的
1. **结构化的规格说明**：每个功能有清晰的验收标准
2. **可执行的测试**：TDD 红绿重构循环，有完成标准和判停条件
3. **清晰的 trigger**：description 字段明确说明何时调用、何时不调用
4. **质量保障**：每个 skill 通过系统化反馈循环
5. **架构改进建议**：基于深模块设计哲学的具体候选
6. **可安装**：skills 被安装到 `~/.openclaw/skills/` 目录，可以真正被调用

### 用户不期望看到的
- ❌ 简单的代码片段（那是普通代码生成工具的工作）
- ❌ 没有测试的实现（那是 vibe coding 的职责）
- ❌ 作者人设角色扮演（那是 nuwa-skill 的职责）
- ❌ 没有经过反馈循环的代码（听起来能跑但不能维护）
- ❌ 没有 CONTEXT.md 的项目（无法建立共享语言）

## 🔧 技术偏好

### 用户可能关心的
- **OpenClaw 兼容性**：skills 可以安装到 `~/.openclaw/skills/` 目录
- **darwin-skill 兼容**：test-prompts.json 遵循 darwin-skill 格式，可以自动进化
- **断点续跑**：中断后可以从任意阶段恢复，不浪费时间和 token
- **审计轨迹**：保留 candidates/ 和 rejected/，方便事后审查和捞回

### 用户可能不关心的
- 底层实现细节（除非用户明确问）
- Token 消耗统计（除非用户明确要求优化）
- 并行 vs 串行的技术选择（除非影响速度显著）

## 💬 反馈循环

### 用户可能提供的反馈
1. **"骨架理解不对"** → 回到阶段 0，重新分析
2. **"这个候选应该通过/不通过"** → 调整三重验证标准
3. **"trigger 不准"** → 回到阶段 2，修改 description 和 A2 段
4. **"测试通过率太低"** → 回到阶段 2，重做 RIA++ 构造
5. **"安装位置不对"** → 重新安装到正确位置

### 如何处理反馈
- **记录反馈**：在 `memory/YYYY-MM-DD.md` 中记录用户的反馈和调整
- **更新文档**：如果反馈揭示了常见问题，更新 TOOLS.md 中的"常见错误模式"
- **持续改进**：定期回顾反馈，优化流水线和验证标准
