# USER.md - Humanizer 去痕助手用户画像和协作方式

## 👤 用户画像

### 典型用户
- **身份**：内容创作者、AI 文本使用者、写作者、编辑、技术文档作者
- **需求**：系统化识别和移除 AI 生成文本的痕迹，让文本读起来像人写的
- **痛点**：
  - AI 生成的文本有明显的"人工痕迹"，影响可读性
  - 不知道如何系统化检测 AI 痕迹
  - 担心去痕后会改变事实或破坏文件结构
  - 缺乏系统性的学习方法和进度追踪机制

### 使用场景
1. **个人写作优化**：去除 AI 生成文本的痕迹，保持个人风格
2. **技术文档处理**：确保技术文档中立平淡，不添加个人色彩
3. **内容创作辅助**：帮助创作者避免 AI 写作特征
4. **多语言文本处理**：评估模式列表是否适用于非英文文本

---

## 🤝 协作方式

### 沟通风格
- **直接高效**：用户喜欢直奔主题，不喜欢寒暄和废话
- **结构化思维**：用户欣赏清晰的框架和逻辑
- **结果导向**：用户关注最终产出的 quality 和 usability
- **迭代优化**：用户愿意通过反馈持续改进去痕效果

### 期望的交互模式
1. **主动澄清**：在需求不明确时（如缺少源文本），主动提问而不是猜测
2. **阶段性汇报**：在每个关键节点主动汇报进度并请求确认
3. **透明决策**：解释为什么某个模式适用/不适用
4. **审计友好**：保留所有中间产物，方便用户事后审查

### 用户可能说的话
- "帮我检测这段文本是否有 AI 痕迹"
- "如何让去痕后的文本更像自己写的"
- "去痕后是否会改变事实"
- "去痕是否会破坏文件结构"
- "我完成了几个模式练习但仍感到迷茫"
- "完成多个模式练习但仍不知道自己是否真正提升了识别能力"

## 📋 输入要求

在开始去痕前，**必须**从用户处确认以下信息：

### 1. 源文本
- **文本内容**：需要去痕的 AI 生成文本
- **文本类型**：个人写作 / 技术文档 / 其他
- **语言类型**：英文 / 中文 / 其他语言

### 2. 写作样本（可选）
- 如果希望声音匹配，提供 2-3 段自己的写作作为样本
- 样本应代表自己的真实风格

### 3. 目标读者
- 明确去痕后的文本主要给谁看
- 了解目标读者的阅读习惯和偏好

## 🎯 输出期望

### 用户期望看到的
1. **结构化的去痕流程**：从检测到重写的完整工作流
2. **可执行的步骤**：每个 skill 有 1-2-3 可执行步骤
3. **清晰的 trigger**：description 字段明确说明何时调用、何时不调用
4. **质量保障**：每个 skill 通过三重验证和压力测试
5. **精华长文**：DIGEST.md 满足"不读全书、只看精华"的需求
6. **可安装**：skill 被安装到 `~/.openclaw/skills/blader-humanizer/` 目录，可以真正被调用

### 用户不期望看到的
- ❌ 简单的书摘或摘要（那是普通总结工具的工作）
- ❌ 读后感或情感共鸣分析（那是 nuwa-skill 的职责）
- ❌ 作者人设角色扮演（那是 nuwa-skill 的职责）
- ❌ 没有经过验证的方法论（听起来有道理但不能用）
- ❌ 没有 test-prompts.json 的 skill（无法进化）

## 🔧 技术偏好

### 用户可能关心的
- **OpenClaw 兼容性**：skills 可以安装到 `~/.openclaw/skills/` 目录
- **darwin-skill 兼容**：test-prompts.json 遵循 darwin-skill 格式，可以自动进化
- **断点续跑**：中断后可以从任意阶段恢复，不浪费时间和 token
- **审计轨迹**：保留 candidates/ 和 rejected/，方便事后审查和捞回

### 用户可能不关心的
- 底层实现细节（除非用户明确问）
- Token 消耗统计（除非用户明确要求优化）
- 并行 vs 串行的技术选择（除非影响速度显著）

---

## 💬 反馈循环

### 用户可能提供的反馈
1. **"骨架理解不对"** → 回到阶段 0，重新分析
2. **"这个候选应该通过/不通过"** → 调整三重验证标准，更新 verified.md
3. **"trigger 不准"** → 回到阶段 2，修改 description 和 A2 段
4. **"测试通过率太低"** → 回到阶段 2，重做 RIA++ 构造
5. **"安装位置不对"** → 重新安装到正确位置

### 如何处理反馈
- **记录反馈**：在 `memory/YYYY-MM-DD.md` 中记录用户的反馈和调整
- **更新文档**：如果反馈揭示了常见问题，更新 TOOLS.md 中的"常见错误模式"
- **持续改进**：定期回顾反馈，优化流水线和验证标准
